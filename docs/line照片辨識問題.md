# LINE 照片辨識問題與修正紀錄

紀錄日期：2026-11-02（Asia/Taipei）。涵蓋 2026-11-01 至 2026-11-02 的排查、修正與上線結果。

## 目前操作流程

傳送圖片後顯示「要如何處理這張圖片？不處理無須理會」，提供：

- **新增公告**：以公告方式辨識單張圖片。
- **連續圖片公告**：收集同一傳送者在同一聊天室的後續圖片，按「完成並建立」才處理。
- **辨識 Case 表／行程**：走分類辨識流程，不強制轉成公告，不需先輸入指令。

未點選時不下載圖片、不呼叫 AI、不新增公告。未操作的選項五分鐘後失效；新圖片會取代尚未操作的舊提示。選項綁定原傳送者與原聊天室。

## 問題與處理

### 1. 同一張圖片重傳後新增重複公告

最初公告儲存流程直接逐筆新增，未檢查既有資料。

加入 SQLite 交易內的圖片指紋與內容比對，記錄圖片與公告的關聯。相同內容會忽略空白、換行與 Unicode 全半形差異；標題不同不再阻止內容去重。刪除公告時，其圖片關聯會一併刪除，之後可重新建立。

後續補上逐張指紋檢查，解決同一張圖片在「單張」與「多張批次」之間重傳時漏攔，也排除同一批次中的相同圖片。公告目錄為全域資料，去重不以群組區分。

相關版本：`54bef2c`、`e7c4515`、`c96a929`。

### 2. 與同事溝通用的圖片被誤建公告

主選單截圖中的 Case 分流說明被 AI 當成公告新增。改為傳圖後先由使用者選用途；取消收到圖片後倒數十秒自動辨識的流程。

使用一行提示與 Quick Reply，避免大卡片干擾。LINE Quick Reply 會因聊天室新訊息而消失，並非固定附在原圖片下方；連續圖片收集期間，每次續傳會回覆數量與完成／取消按鈕。

相關版本：`54bef2c`、`e7c4515`。

### 3. 忽略第一張圖片後，後續圖片沒有新增選項

原先尚未確認的圖片會持續收集後續圖片，但只顯示第一次提示。忽略聊天用照片後，後續公告照片因此沒有按鈕，也可能把無關照片混入批次。

改成只有明確選擇「連續圖片公告」才收集後續圖片。其他情況下，新照片取代舊的待確認狀態、產生新提示，舊按鈕失效。

相關版本：`5b28893`。

### 4. Case 表直接上傳卻只能選公告

初版只有先輸入「辨識照片」，才提供分配表／行程選項，直接傳圖會被導向公告流程。

改為所有一般圖片上傳都提供三個用途選項，Case 表／行程選項送入分類辨識，公告選項才固定走公告整併。同步更新主選單說明、功能提示與 README。

相關版本：`399c45c`。

### 5. 關閉 A 群功能後仍疑似運作

檢查確認 A 群的照片辨識與 Case 接收設定已存為關閉；當時執行中的服務仍回報較舊版本，不能只憑此斷定所有現象的唯一原因。

補強使用者圖片與按鈕操作的功能檢查、辨識前後的開關檢查、Case 排程建立時的目標群組檢查，以及定時發送前的再次檢查。從 B 群進入後台設定 A，仍以選定的 A 群 ID 儲存與查詢。

使用者觸發已關閉功能時回覆「XXX功能目前開發測試中...」；定時轉發直接跳過已關閉的群組，不額外推播提示。

相關版本：`54bef2c`、`e7c4515`。

### 6. LINE 預覽的辨識進度一直顯示 00:00

確認停住的位置是 LINE 聊天室的靜態連結預覽，並非點開後的進度網頁。以模擬頁面執行驗證完整網頁會從 0:10 前進至 0:40。

移除頁面初始的 0:00，改為「—」，加入 Open Graph 標題與說明，提示點開查看即時進度；Bot 訊息也註明聊天預覽不會更新。舊訊息可能仍顯示 LINE 的預覽快取。

維持網頁自動更新與完成後回傳群組的方式，未改為 Flex 進度卡片。已送出的 Flex 訊息不能原地持續更新；使用者決定沿用目前流程。

相關版本：`7256c43`。

### 7. 模型啟動等待過久

原設定 `LOCAL_AI_MODELS=local,qwen3.6`，先嘗試 Strata，失敗後才嘗試 Qwen3.6。

正式環境、程式預設與 `.env.example` 改為 `LOCAL_AI_MODELS=qwen3.6`，直接由 Port Monitor 請求 Qwen3.6。保留 Gateway 路由與既有 Gemini 備援規則；沒有有效雲端金鑰時，失敗不會用 MOCK 結果新增資料。

實際啟動加一筆簡短文字測試請求約 75 秒，HTTP 200，Gateway 回報模型已就緒。此數字不是照片辨識耗時，也不保證之後每次啟動都相同。

相關版本：`5a91d29`。

### 8. 跨群重傳仍新增，需人工攔截

查到舊公告沒有圖片指紋，新的 AI 辨識則把同一段用藥規定改寫成條列，標題與內容都與原文不同，既有完全相同比對無法攔截。不能斷定這次圖片必然經過重新壓縮；檔案重新編碼本身也會使 SHA-256 改變。

加入既有公告內容的相似候選檢查，不受群組或建立來源限制，涵蓋人工與舊版建立的公告：

- 圖片指紋或正規化後內容相同：略過新增，附公告目錄。
- 內容高度相似：先不新增，列出候選公告標題與目錄入口，讓使用者核對；新版規定請編輯原公告。

相似檢查使用正規化後的文字雙字片段集合，兩邊的重合比例均至少 65%，且兩段文字均至少 30 字元。這是疑似重複攔截，不是語意相等證明；用藥劑量、科別或限制有變動時也可能需要核對。疑似候選不寫入「已確認相同圖片」關聯。

使用實際舊公告與改寫文字建立回歸測試，確認攔截，並確認不相干公告仍可新增。既有重複公告未自動刪除。

相關版本：`52d2647`。

## 後續補強：疑似重複公告暫存與補救

疑似重複的辨識結果改存入 SQLite `note_reviews`，保留完整標題、文字、來源群組／傳送者、圖片指紋、既有公告參照與處理紀錄，不因 Bot 重啟消失。自此版本起的新攔截會暫存；先前未儲存的攔截結果不會自動回填。

公告目錄增加「待確認公告」區塊，可展開比對既有公告，並選擇：

- **補建公告**：直接使用暫存文字新增，略過 AI 辨識與相似度攔截。以資料庫交易防止重複點擊建立多筆，保留處理者與時間。
- **確認重複，捨棄**：移出待確認列表，不新增公告；資料庫保留處理紀錄。

Bot 的攔截回覆提供目錄待確認區入口。新 API 沿用既有登入與人員白名單驗證，不對外公開暫存內容。原公告刪除後，待確認內容仍可補建。暫存保存的是辨識文字與來源指紋，並非原始圖片檔。

驗證：28 項測試通過，涵蓋重複暫存合併、原文保存、原公告刪除後補建、重複提交只建一筆，以及捨棄留存處理紀錄。另以本機隔離測試資料確認待確認區的畫面、比對入口與補建後列表更新；未以真人 LINE 帳號操作登入流程。

### 待確認公告保存期限與倒數

待確認內容自建立起保存 7 天，頁面顯示「剩餘 X 天 X 小時」，不足一小時顯示「剩餘不到 1 小時」，並提供到期時間提示。到期停用按鈕，後端在讀取／處理前檢查期限；啟動時與每分鐘排程清除逾期且仍待確認的內容。已補建公告與已完成處理紀錄不受此待確認期限影響。到期後不可補建；計時以手機時間顯示，後端以伺服器時間判定是否允許處理。

驗證：29 項測試通過，包含到期邊界不可補建且不刪除正式公告。


## 群組 @all 訊息自動記錄

正式 LINE 全體提及訊息（`mention.mentionees[].type = all`）自動保存為公告／提醒，移除全體提及標籤並保留其餘原文字，第一行作為標題（最多 40 字元）。不呼叫 AI，也不自動建立行事曆或定時推播。

僅限群組，純文字輸入或引述 `@all`、單獨標記全體而無內容、個人提及不觸發。後續圖片與一般聊天不會自動併入。沿用「注意事項」功能開關；關閉時回覆開發測試提示。

使用 LINE 訊息 ID 記錄來源，跨群組相同內容仍共用去重；疑似重複保存到 7 天待確認區，可不經模型直接補建。記錄來源群組、傳送者與可取得的更新者姓名。31 項測試通過，涵蓋正式提及／普通文字區分、重送、跨群去重、疑似重複與停用開關。

LINE 格式依官方 Messaging API reference：https://developers.line.biz/en/reference/messaging-api/#wh-text


## @All 改為暫存、AI 草稿與人工確認發布

本次更新取代前述 @All 直接發布行為：所有新的 @All 文字先暫存 7 天，不直接建立正式公告。已有正式公告的相同內容仍略過；重送或跨群傳送相同待確認內容共用一筆暫存。

每筆待確認公告（包含疑似重複圖片辨識結果）提供「AI 整理」，由本機 Qwen3.6 只整理現有文字，產生草稿標題與內容，不重新辨識圖片、不自動發布。原文與 AI 草稿分欄保存，頁面可修改草稿後按「確認發布草稿」；亦保留「原文直接補建」與「捨棄」。發布使用人工確認的內容並略過再次相似度攔截，以交易確保重複提交只建立一筆。

整理使用背景工作，API 立即回傳並由頁面查詢狀態，避免長時間等待超過中繼請求期限。同筆整理進行中不重複啟動；失敗顯示原因且保留原文，可重試。草稿持久保存，但執行中工作隨服務重啟中斷；原本的 7 天期限不因 AI 整理延長。到期或已處理時，AI 結果不會發布。

驗證：33 項測試通過，包含 @All 暫存與跨群去重、AI 草稿保留原文、整理不自動發布、人工修改後發布、重複點擊防重、AI 失敗重試。以隔離範例資料檢查頁面從整理中切換至可編輯草稿。真人 LINE 登入流程未重新操作。
